# OLGA — переходный процесс при переключении на обход МБСНУ

## Задача

Цель демонстрации — через агента и MCP запустить подготовленный сценарий OLGA и
проанализировать переходный процесс при переключении на обход МБСНУ.

Расчёт длится 96 ч. Переключение начинается на 48-м часу и занимает 60 с. За это
время открывается байпас, закрывается ветвь сепаратора, а подача источника `Pump`
снижается до нуля.

По результатам расчёта нужно проверить, как перераспределяются расходы между
байпасом и ветвью сепаратора и сохраняется ли подача на АГЗУ-2. Для демонстрации
нужно построить графики расхода и давления во времени.

### Пример запроса

> Запусти подготовленный сценарий переключения на обход МБСНУ в OLGA. Построй
> графики расхода и давления, покажи перераспределение расходов и проверь,
> сохранилась ли подача на АГЗУ-2.

## Архитектура

```text
запрос инженера
      ↓
agent.py → src/agent → MCP-клиент
                         ↓
                mcp_server/server.py
                         ↓
              адаптер инженерного ПО
                         ↓
                  симулятор и модель
```

Агент и MCP-сервер являются отдельными компонентами. Код агента не импортирует
OpenServer, COM или SDK симулятора. Вендорские зависимости находятся только в
`mcp_server/`.

## Структура

```text
agent.py                 точка входа run(request, ctx) -> AgentResult
src/agent/               цикл, схемы, промпты и MCP-клиент
mcp_server/              локальный сервер и адаптер выбранного ПО
tests/                   тесты контракта и заглушки адаптера симулятора
notebooks/demo.ipynb     заготовка демонстрационного ноутбука
docs/                    каталог для документации
project.yaml             метаданные проекта
```

## Быстрый старт

Выполняйте команды из каталога `well-agent`.

### PowerShell

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pytest
```

### macOS и Linux

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pytest
```

Для запуска локального MCP-сервера по `stdio` выполните
`.\.venv\Scripts\python.exe -m mcp_server.server` в PowerShell или
`.venv/bin/python -m mcp_server.server` в macOS и Linux.
Из активированного окружения PowerShell можно также использовать скрипты
[`scripts/run_mcp.ps1`](scripts/run_mcp.ps1) и
[`scripts/run_tests.ps1`](scripts/run_tests.ps1).

### Проверка доступа к LLM

Скопируйте `.env.example` в локальный `.env` и заполните `LLM_BASE_URL`,
`LLM_MODEL` и `LLM_API_KEY`. Команда проверки сама читает `well-agent/.env`.
Одноимённые переменные окружения имеют приоритет над файлом.

```sh
.venv/bin/python -m scripts.check_llm
```

В PowerShell используйте `.\.venv\Scripts\python.exe` с теми же аргументами.
Команда отправляет один нейтральный запрос к настроенной модели, проверяет ответ
по строгой JSON Schema и выводит идентификатор модели и результат. MCP и OLGA
для этой проверки не требуются.

### Разбор запроса через LLM

```sh
.venv/bin/python -m scripts.parse_request "Запусти подготовленный обход МБСНУ на 96 часов. Начни переключение на 48-м часу и выполни его за 60 секунд. Покажи расходы и давление."
```

Команда печатает проверенный JSON с действием, ID сценария, временами и
запрошенными показателями. Время сохраняется как число с единицей, например
`{"value": 48, "unit": "h"}`. Для пропущенных времён и ID сценария возвращается
`null`. Команда разбирает запрос независимо от MCP.

### Проверка запроса по MCP-манифесту

`agent.run(request, ctx)` разбирает запрос, переводит время в секунды и вызывает
`read_case_manifest` после проверки явно заданных времён. Для запроса без ID
укажите `MCP_CASE_ID` в локальном `.env` или `mcp_case_id` в `BenchContext`.
На тестовом сервере используется `mbsnu_bypass_96h`.

Проверенное расписание возвращается в `validated_request.schedule`. В
`validated_request.parameter_sources` виден источник каждого времени
(`request` или `manifest`). Статус `ok` на этом этапе означает завершённую
валидацию. При отказе поле `rejection` содержит причину и полученное значение.

```sh
.venv/bin/python -m pytest -q tests/test_request_validation.py
```

Эти тесты используют подставной ответ LLM и реальный stdio до тестового
MCP-сервера с фиксированным расписанием.

### Проверка stdio-клиента

Для интерактивной проверки всей клиентской цепочки на отдельном тестовом сервере
запустите из `well-agent`:

```sh
.venv/bin/python -m scripts.demo --test-mcp
```

CLI использует настройки Groq из `.env`. Введите «Запусти подготовленный обход
МБСНУ на 96 часов с переключением на 48-м часу за 60 секунд. Покажи расходы
и давление». Проверьте модель, копию, расписание и действия. Ответ `да`
запускает показанный синтетический план. Ответ `нет` или закрытие ввода
сохраняет отказ. После результата можно ввести второй запрос, например
«Начни переключение на обход МБСНУ через минус один час». Пустая строка
на приглашении ввода запроса завершает CLI.

Без флага `--test-mcp` CLI выполняет текущую валидацию через штатный MCP-сервер.
Полный тестовый прогон помечен `TEST MODE`. Таблица, исходные данные и два
SVG-графика построены по синтетическим рядам. CLI печатает путь к журналу
`logs/<trace_id>.jsonl`. Решение пользователя, идентификаторы плана и запуска,
вызовы и ответы связаны одним `trace_id`. При таймауте журнал сохраняет
последний известный статус и `run_id`. Артефакты находятся в `logs/<run_id>/`.
Состояние тестового сервера хранится в памяти до закрытия его процесса.

Для проверки таймаута выполните команду и подтвердите тестовый план.

```sh
.venv/bin/python -m scripts.demo --test-mcp --test-outcome stuck --timeout 2 --poll-interval 0.5 --request "Запусти подготовленный обход МБСНУ"
```

Варианты `--test-outcome failed` и `cancelled` воспроизводят соответствующие
конечные состояния. Ключи и токены в журнале скрываются. По умолчанию
каталог `well-agent/logs/` исключён из Git.

### Отдельная проверка транспорта

Из `well-agent` запустите тест рукопожатия, списка инструментов и чтения манифеста.

```sh
.venv/bin/python -m pytest -q -s tests/test_mcp_stdio.py::test_stdio_manifest
```

В PowerShell используйте `.\.venv\Scripts\python.exe` с теми же аргументами.
Тест запускает отдельный процесс из `tests/fixtures/`. Строка `TEST MODE` в выводе
обозначает тестовый манифест. Для проверки штатной команды с текущим сервером
запустите `tests/test_mcp_stdio.py::test_default_stdio_command_uses_project_server`.

Клиент запускает сервер тем же интерпретатором Python из каталога `well-agent`.
В `BenchContext` можно задать `mcp_server_args`, по умолчанию
`["-m", "mcp_server.server"]`, и `mcp_timeout_s`, по умолчанию 10 с на операцию.
Для stdio оставьте `mcp_server_url` пустым. При непустом запросе точка входа
проверяет доступность MCP и возвращает `error` при сбое. Сценарные инструменты
и подтверждение описаны в [черновике контракта](docs/mcp-contract-draft.md).

## Что уже есть

- контракт `run(request, ctx) -> AgentResult`
- Pydantic-схемы результата, чисел и журнала
- порт `ToolGateway` и stdio-клиент `McpToolGateway` в [`src/agent/tools.py`](src/agent/tools.py)
- типизированный разбор запроса через LLM в [`src/agent/intent.py`](src/agent/intent.py)
- локальный MCP-сервер с инструментом проверки конфигурации `get_simulator_status`
  и инструментом `run_simulation`, который передаёт вызов адаптеру симулятора
- тесты контракта агента, адаптера и stdio-клиента

## Что предстоит реализовать

- Согласовать контракт с участниками 2 и 3, подключить рабочий сервер
  к подтверждению, опросу статуса и чтению результатов.
- В [`SimulatorClient.run_case`](mcp_server/simulator/client.py) подключить OLGA,
  запускать подготовленный сценарий и получать временные ряды расхода и давления.
  Добавить обработку таймаутов, ошибок симулятора и лицензии.
- Добавить анализ перераспределения расходов и подачи на АГЗУ-2, построение
  графиков, заполнение демонстрационного ноутбука и тесты с эталонными результатами
  и ожидаемыми отказами.

## Ограничения шаблона

Каркас не подключён к промышленному ПО и не выполняет расчёты. Метод
`SimulatorClient.run_case` завершает работу явной ошибкой, пока команда не добавит
адаптер выбранного симулятора.

Для запуска из Colab нужен доступный по сети MCP endpoint. `localhost` в Colab не
указывает на компьютер, где установлен симулятор.
